# Native engine / GK1 review — 2026-10-31

**Recommendation: retain the native engine, finish the useful SCI2 work, and make the query, predicate, and placement contracts honest before shipping protection.** The immediate work is integration and focused repair: reuse the later branch's retained semantics, distinguish candidate evidence from established gameplay feasibility, preserve the actual preparation predicate, and cover every unsafe source route. A shared action contract is the intended direction, but neither a wholesale canonical-action migration nor a new coupled analysis is a prerequisite to the first playable result. Undertake those deeper changes only when a concrete milestone shows that the existing representation or queries cannot preserve a needed relationship.

GK1 integration failed at several different handoffs. Some important frontend facts were missing; later work repairs several of them. Other facts were already available but lost when translated into independent register availability, item requirements, or a source edit. The original branch produced loadable patches with demonstrably wrong behavior. The later branch produces better evidence but deliberately stops before patching. Neither establishes usable GK1 protection. “No modelling gap left,” “all detectors completed,” and “the patch compiled” are three different claims, none sufficient for that conclusion.

The first implementation milestone should be a **working ritual-entry patch**, covering both ways of entering the ritual and distinguishing carrying the crocodile mask from having used it. That is a finite, source-supported mechanism which tests detection, state predicates, placement coverage, compilation, and gameplay together. Follow it with the confessional/Grace-room preparation chain. Complete these using the available semantics where they suffice; do not require another consolidation, a universal SCI interpreter, or another permanent preparation model first.

## What works, and what “works” must mean

The native stack has valuable capabilities: typed decompilation, vocabulary discovery, bounded Script compilation, room/region/caller attribution, inventory identity, automatic anchors, geometric checks, SCC reachability, guard rendering, source placement, and compiler/resource packaging. Its established successes should be preserved.

The original structural abstraction fits many earlier cases. LSL2's raft, `build/ir/src/rm138.sc:196–225`, explicitly tests possession, consumes spinach dip on the losing branch, and branches on other food. Boarding in `rm57.sc` leads through an explicit `newRoom` boundary. The machine compiler and item/room requirements have a close correspondence to these source mechanisms. KQ6 already extends beyond simple possession: `rm440.sc:435` and `minoTrigger.sc:86` set `scarfOnMino` from the inventory verb, and later states test that property. Property lowering and item costs are reusable achievements, not obsolete SCI0 assumptions.

But the opening claim in `src/scc_core.py` that inventory does not matter within an SCC is a restricted abstraction, not a theorem about Sierra games. GK1 advances days while revisiting the same city, returns from a shared interrogation room to its caller, and switches twelve Hounfour scenes inside room 800. Location alone omits the state that determines available actions and future obligations. The problem is the density and interaction of such mechanisms, not a clean SCI0/SCI2 dividing line.

An especially useful **positive repaired mechanism** is the artist's reconstructed veve pickup. `build/sweep/gk1/src/neJackson.sc:1264–1273` requires day 3, flags 231 and 232, and an unset flag 233; it then sets 233 and grants item 38 in the same handler branch. Splitting those effects admits an impossible state: collection completed, paper still missing.

Commit `ce7bdf1` retains handler paths by source identity. `handler_actions.retain` and `sci2_dependencies.build/writes` keep the grant with the write; a query banning item 38 cannot take the completed pickup and remain item-less. The saved `build/review_gk1_effects/actions.json` contains nine passing controls, including the actual source action, missing prerequisites, wrong day, successful pickup, and removal of the pickup-flag stranding. This is meaningful semantic progress. It does **not** establish that all later day-related paper rows are correct.

Likewise, `3faa16f` repairs a real frontend deficit. In `rm710.sc:1570–1608`, tile identity is computed from `cel`, parity, and `48 + temp1`; frames 7 and 12 are immovable. Previously literal-only acquisition extraction gave the tile group no sources. `sci2_item_values.py` resolves observed finite values into the existing acquisition representation. Saved tile controls verify all ten movable frame/item pairs, their inverse placement mapping, and disappearance of the no-source group. The later report records three pickup sites. Preserve this repair, while retaining its limitation: a possible value set is not a simultaneous grant of every tile or a full model of tile placement state.

For this project, useful end-to-end support means: a reachable original-game prefix, an optional commitment that loses a still-needed possibility, a successful preparation alternative, a guard at every unsafe route before irreversible effects, and runtime confirmation that safe play proceeds. The following failures show why intermediate success is insufficient.

## Three consequential failures, traced to their first bad handoff

### 1. Confessional preparation becomes an impossible possession demand

The game source is unambiguous. In `rm455.sc:823–830`, using the rod performs `(global0 put: 60)` and raises flag 280. The adjacent signal-device branch removes the selected device and raises flag 281. In `sHRoom6.sc:130–137`, entering from the elevator with both flags raises flag 351. This is setup whose success survives after the inventory objects have been consumed. Later `sHRoom8` tests flag 351, and its state 0 sets `timeForCeremony: 1` at line 71, closing the earlier scene structure.

The emitted patch at **`build/gk1_patch_v2/patch_project/src/rm455.sc:87`** requires `has: 60` when flags 273 and 271 select the downstairs exit. It also requires item 69 and a paper group. After the correct rod deposit, the rod conjunct is false. Keeping the rod satisfies that conjunct while leaving preparation unfinished. This is a source-proven obstruction, regardless of whether the compiled pair loads.

The first bad handoff is not decompilation: the removal and flags are explicit. It is the reduction of a preparation obligation to a carried-item frontier, followed by `guards.render_frontier` (`src/guards.py:1478`) rendering that frontier as current ownership. Existing owner-based `fold_respell` rules do not express this particular flag-based success. The old oracle compounds the problem: R2 passes when rod and signal-device names appear somewhere in the detector union (`src/test_gk1_ground_truth.py:248`), without requiring the deposit mechanism or correct predicate.

The later branch substantially fixes the *representation*. Its retained `pipe-regen/sci2-detection.json` contains a scene-boundary obligation for register 711, corresponding to flag 351, with the producer in script 806 state 6 requiring flags 280/281. It also records both guises as carry-ins to scene 808, sourced in scene 807. This should be completed and reused. It does not need another preparation engine. However, `guards.py` still has no `scene_carryins` consumer, and `pipeline --sci2` requires `--report`. The corrected fact has not reached a trusted emitted guard.

### 2. Mask detection is converted into a guard on the safe route

`bayouMaze.sc:1894–1910`, `maskAction::doVerb(31)`, sets flag 216 and starts `letsGo`. That is the successful preparation action. Independently, `passageExit::doit` at lines 2066–2081 selects state 16 for a ritual passage; `roomScript` state 16 starts `letsGo` at line 1524. That route does not test the mask. In `bayouRitual.sc:158–166`, state 5 tests flag 216 and hands control to `killGabe` when it is clear.

The old detector can identify the room 490→480 obligation. The generated **`build/gk1_patch_v2/patch_project/src/bayouMaze.sc:1898–1916`** instead wraps the mask-use action with a possession test. The separate walk-in route remains open. Carrying the mask and using it are different states; protecting one arming does not protect all routes to the crossing.

Here the first demonstrated bad handoff is **finding → placement**. `trigger.find_trigger` chooses `sites[0]`, then the first suitable controllable `setScript` arming (`src/trigger.py:1303–1365`); it returns one placement, not evidence that every unsafe route crosses it. Changing the condition at that same site to flag 216 would be worse: it would block the action that sets the flag.

The later branch reports flag 216 as an arrival-state obligation (reg 576 in the regenerated input) and supplies bad/good projection controls. That is a better predicate. It is classified as requirement evidence, appropriately: such controls do not yet show a reachable, optional preparation loss or complete source placement. A correct patch must allow the mask-use action and intercept the independent unprepared departure before control loss/scene transition. The boundary is accepted here under the project's prior-screen-death scope, not as a claim that every immediate death is a softlock.

### 3. Conversation availability, callback execution, and day feasibility are conflated

The proposed R4 story assumed Cazaunoux's topic 61 provided an independent first bracelet viewing without flag 44. The actual dependency chain contradicts that premise:

* `GKTeller.sc:80–97` offers global topic 8 only when flag 44 is set.
* `hartridge.sc:217–227` turns topic 8 into callback 59; callback 59 raises flag 67.
* Topic 61 is offered only when flag 78 is set and 421 is clear (`hartridge.sc:178`). Flag 78 is raised after viewing the bracelet (`rm280.sc:749`); 421 after making the mold (`:810`). It is a repeat route.
* Room 280 opens the bracelet sequence under flag 67 (`:108`); the mold is item 40 (`:794`). Giving it to Sam raises flag 256 (`napoleon.sc:838–858`), and day 3's `endDay` requires 256 (`theMapPrint.sc:247`).

This strongly refutes the claimed day-4-without-flag-44 prefix. It is a source-supported conclusion, not a newly executed full-game reachability proof. A contrary ordinary-input route would overturn it. The old R4 test explicitly seeds `producible_seal(123, 4, 370, flag44, 0)` and accepts its answer; that does not establish that the seeded player can exist or that the normal detector discovered the case.

There is also a concrete frontend loss behind the misleading freedom. Root `vocab._prop_assign_sites` treats `++iconValue` as an unknown assignment to any callback. `_lower_followup_arms` only initially settles cases with a `showCases` condition or global-band condition. Cazaunoux's personal 41 is listed by `setPersonals`, has no such condition, and increments `iconValue`. It therefore remains an unsettled taint source; callback 59 cannot acquire its proper predecessor condition through this algorithm. Cases can remain unconditional. This is the first bad handoff: **callback protocol → flat guarded handler**. Downstream day-window reconstruction cannot reliably repair a lost invocation history.

The later `sci2_dialogue.py` explicitly models selection, preparation, speech, and callback phases, with a carried selection value; callback labels are not menu entries. Its saved regenerated report lowers 30 dialogues and reports no dialogue-boundary failures for that input. This is a completed repair class worth retaining. It remains bounded and reports limitations for dynamic invocations, aliasing, and unsupported protocols. Its success does not make the subsequent independent-projection feasibility queries exact.

## Other integration boundaries

**Resources, decompiler, and VM.** The available IR and source support all three diagnoses above. There is no evidence that interpreting every SCI kernel is prerequisite to these fixes. There are real resource defects: root `sci_resource.py:186` rejects `decomp > 0xFFFF` even in its wide-header branch, rejecting the 29 legal large resources counted here. Its `volume_format` comment incorrectly blames view 0's map location. Method-32 decompression is another separate limitation. These affect confidence in graphics/resource coverage, not the already-visible confessional logic. The later branch's resource reader remains at the baseline, so the old backend/resource changes must be reconciled selectively.

The compiler wall was partly a mistaken capability assessment. `a47d9a9` exposed the vendor's existing `sciVersion2` backend through `tools/scicompile/main.cpp:588` and supplied kernel vocabulary. The historical patching record reports 211/212 source scripts compiled; the remaining multiargument `loop:` property send in `napoleon.sc` is a round-trip limitation, not proof of a missing SCI2 compiler. Four script/heap pairs are retained in `build/gk1_patch_v2/patch/`. The historical account reports script instantiation and boot checks with corruption controls; I did not repeat those checks or independently verify their runtime logs. It explicitly reports no gameplay test. Its claim that R5 is protected is disproved by the two source routes above.

**Entries and captured values.** The old source already demonstrates why global write bags are insufficient: `napoleon.sc:1287` writes interrogation subject 34 immediately before arming `askBartender`; Script parameters and `register` carry the chosen branch through subsequent states. Root adds `entry_gwrites`, `entry_ggets`, and parallel entry metadata to repair such losses. Later `sci2_arguments`, `register_flow`, ordered-prefix handling, and event membership address related gaps. These should become parts of the shared action contract, not separate reconstructions in each detector. Named entries, instances, callbacks, and disposal matter; not every `PARK` is termination, and not every wait permits advancing into the next state.

**Requirements and reachability.** A source room, an available pickup, a currently faced requirement, and an action that necessarily grants an item are distinct facts. Current code knows this in places—`source_guards`, `required_guards`, `_source_live`, `_need_live`, ban/grant coupling—but individual consumers apply different slices. `_need_live`, for example, can leave a need live when its projection does not contain the relevant condition. Other paths use room sets or historical item costs. These permissive answers are useful candidate evidence; they cannot demonstrate a single executable preparation-loss story.

**Synthesis and verification.** Root reporting enumerates a handwritten subset of detectors. Later `analysis.py` fixes execution coverage through declarations, memoized results, explicit roles, and failures for unclassified methods. Preserve it. But `complete` means every registered method returned, not semantic completeness. Later `guards.verify` still compares `analyze` item identities and group identities before/after; it does not verify all scene/state obligations. Source placement happens after the old verification stage. An unplaced spec and a wrong-route edit must not inherit a model-level “fixed” verdict.

## History: what the attempts actually established

The original branch accumulated a long series of locally motivated repairs. It broadened vocabulary and flag stores, priced previous-room returns, recognized scene carry-ins, and attempted to date acquisitions and demands against day progression. These changes are understandable responses to real source mechanisms.

However, the `4dab124` record describes five reverts before the day-domain fallback landed with consumer-window/prune iteration and era-forced filtering. Earlier attempts (`28d91e1`, `4c5357b`, `1ab1621`) alternately exposed free day advances, phantom reachability, or changed candidate rows. The key lesson is a feedback loop: missing transitions made a finding appear correct; adding real transitions invalidated it; new restrictions were needed to recover the intended story. Re-pinning expected output is not independent confirmation of that story.

`c0c1d93` fixes a concrete historical-cost omission: `prev == 302` implies an earlier entry into 302, which requires both tomb sketches; the modal self-return must not cheapen that price. The source-backed repair is useful. Its accompanying “no modelling gap left” claim does not follow. The false R4 prefix, confessional predicate, and mask placement remain counterexamples to end-to-end correctness. Classifying residual false positives as policy decisions does not establish the missing feasibility proof.

The later branch begins again from main and improves actual semantics: resource-backed dialogue, selection/callback phases, computed routes, ordered counters, Script captures/events, scene obligations, source-identified grouped writes/grants (`ce7bdf1`), and computed acquisitions (`3faa16f`). `f7a496e` carries previous-room context in joint projections rather than deleting modal return edges. `fb72351` retains all dependency products derived by its bounded rule and shares equivalent queries. This repairs coverage lost to allocation caps; it does not close dependencies outside the rule, whose reported limit is three cycle registers plus one return-context register.

`3dba3f8` then deletes the unused preparation/arming engine and consolidates several lowerings and transition operations. The dirty second pass consolidates variable effects, call resolution, local-write selection, pricing, and machine destinations. Do not recommend doing those same removals again. Remaining duplication is chiefly a contract problem: several layers evaluate or summarize the same behavior for different consumers, while legacy and SCI2 paths still have different semantic policies. Merely moving helpers into smaller files will not resolve that.

The retained old review run says **1,038 passed, 15 known-red, zero unexpected/crashed**, including failing goldens and emission comparisons. That is agreement with a declared failure set, not a green correctness gate. The later consolidation evidence is stronger for preservation: 1,461 checks, five equal snapshot/emission surfaces, and 1,129 equal emitted files. It still provides no GK1 gameplay validation. The separate bound-reference audit (`writes-bound-gk1.json`) compares 467,773 successor queries, including 289,267 action-path queries, with no disagreement; this matters because an earlier differential shared the newly rewritten action helper on both sides. Preserve the corrected evidence scope.

## Cost and structural limits

The old `IrSccReach` rebuilds causality across `_inroom`, `_rstep`, `_inroom_own`, `_wbranch`, `_cogrants`, `_emeta`, machine entry/state musts, closure tables, and restricted projections. Conditions are repeatedly flattened, then recovered by specialized passes. `_pclose` accumulates possible values and items; contradictory values can remain available together. Intersecting answers from separate projections does not establish a common path or common state. This is a mathematical limitation, not a profiling guess.

One correctness defect is particularly concrete: root `_pclose_pass` returns after 64 sweeps even if it has not reached a fixed point. The retained `closure-order.log` contains a 70-edge chain that reaches the goal in forward table order but only state 64 in reverse order. The reviewed source still has that unconditional bound. An incomplete increasing closure is an under-approximation; using absence from it to prove impossibility contradicts its advertised permissive contract. Budget exhaustion must return unknown, never “unproducible.” This is a locally repairable correctness bug, not by itself an argument for redesign. Other hard bounds need the same directional audit.

The stronger argument concerns actual callers in the **latest dirty SCI2 snapshot**. `missability.register_strandings`, around lines 6168–6207, passes a room set from an optimistic projection walk to `softlock_policy.successful_continuation`. That helper returns `bool(goals & future)`; the caller treats the positive result as the condition that “some equipped player still wins.” A path in one projection does not establish that existential statement in the game. `_flip_predecessors` requires a connecting successor for enriched/action projections, an important repair, but explicitly keeps the older different-value-at-the-same-room contract for other projections. The resulting candidate rows feed register guard derivation.

Similarly, `sci2_scenes.findings:221–233` computes goal controls for one register, then separately checks that its accepted and bad values occur at room 800. It does not establish their joint feasibility with the active scene, ceremony latch, entry conditions, and held items. The source supports the particular flag-351 obligation; these controls alone are not its proof. This distinction matters precisely because the later branch has retained the needed scene facts: it should use them when validating promotion, rather than rediscover them in a new engine.

These callers may honestly emit **candidates**; their existence is not a newly demonstrated false-positive gameplay trace. Centralized typed query results and refusal to promote unvalidated candidates are sufficient to make reporting honest. Promotion needs evidence beyond an optimistic positive answer. First use the retained source relationships, existing joins, and gameplay controls for the concrete milestone. Add coupled feasibility analysis only if those cannot establish the relationship the candidate needs; it may reuse the current machine representation and successor machinery. The evidence warrants changing this contract, not a claim that a new solver or universal replacement state representation is already necessary. Merely renaming a projected positive answer “feasible” would leave the gap unchanged.

Repeated graph work is measured. `review_gk1_projection_complete/summary.json` records a reference run with about 1,894 detector seconds and 14,392,724 KiB peak RSS; its final run has about 905 detector seconds, 3,534,812 KiB RSS, and 255 build seconds. This is a substantial improvement, on that saved experiment. It also changes register rows from 23 to 78 when previously excluded products are retained—an allocation optimization had been affecting coverage.

The later consolidation captures **463 projections and 174,033 reachable states**. Its equivalence audit takes roughly 1,151 seconds; that audit time includes comparisons and must not be advertised as pure analysis latency. Of the saved projection fingerprints, 334 have an identical 117-state set. Equal state sets alone do not prove interchangeable transitions, but they expose an opportunity for query/graph equivalence reuse. `fb72351` already normalizes irrelevant item bans at successor sites; `ReachMemo` already shares SCC closures; compiled projected room edges and the dirty shared transition operator are already implemented. Keep them. Do not claim these optimizations are still missing.

Some added caching has no demonstrated benefit: the retained consolidation counters show three eligible handler-action sites and three template compilations, hence zero hits. More important, detector seed/ban/projection loops still multiply largely overlapping work. Cache by immutable transition relation, relevant dependencies, and explicit query semantics; avoid broad state-dependent invalidation merely because the emitter carries unrelated mutable metadata. Treat further savings as hypotheses until measured.

The latest retained regenerated report has 78 register rows: 20 for reconstructed veve, 19 each for sketchbook, crocodile mask, and oil, and one knife row—**five item identities**, not four. Many rows are alternative projection witnesses. Report them as evidence for mechanisms, not 78 independently validated gameplay failures. The 19 executed detector families are likewise not 19 independent proofs.

A whole-game Cartesian product is not the obvious cure. Existing LSL2 state measurements stop above five million states even with guarded writes. Those are bounded abstract-state experiments, not the true gameplay-state count, but they decisively defeat the assumption that “track everything jointly” will be a cheap refactor.

## Concrete path forward

| Option | Assessment |
|---|---|
| Continue repairing `gk1` as it stands | Reject as the main path. It retains the flawed closure proof, callback approximation, duplicated reconstructions, and wrong protective edits. |
| Finish `sci2-modeling` with wiring and local patch fixes | Appropriate for the first playable slice when accompanied by explicit evidence limits, predicate preservation, complete placement coverage, and gameplay validation. It does not establish general automatic discovery. |
| Focused integration with explicit query/predicate/placement contracts | **Recommended immediate path.** Reuse working semantics and backend. Make deeper action-model or feasibility-query changes conditional on a concrete unmet relationship. |
| Replace the native engine or implement all of SCI | Not justified by this evidence. High cost, discards proven work, and does not itself solve softlock scope or placement. |

Use the later consolidated native branch as the integration base after reviewing and committing its dirty pass through the normal project process. Port the old SCI2 compiler/resource backend separately, including the large-header fix and an explicit unsupported-compression outcome. Do not merge the old closure/day reconstruction wholesale.

The intended responsibilities below describe the direction of the shared contract. Implement only the changes needed for each playable milestone; they are not a second consolidation gate before integration:

1. **Resource/IR and vocabulary layer:** retain resources, selectors, provenance, item identity, and recognized storage/protocol summaries. Give lowered facts stable source identities and reversible renderings. Preserve explicit uncertainty where a resource, expression, callback, or lifecycle is unresolved. Keep unrelated framework inventory tooling outside the verdict path.
2. **Machine/action layer:** preserve the existing `machine`/`compile`/`opmodel` semantics and the source-identified grouping in `handler_actions`. The shared contract should retain source entry and host, pre-state guard, ordered effects, co-writes/grants/removals, captures, continuation or termination, and boundary context. If a milestone demonstrates that the current records lose one of these relationships, repair that handoff; an immutable common action record is then a candidate implementation. Preserve phase-specific dialogue lowering and finite computed-value work. Retiring parallel-entry arrays and derived bags is conditional migration work, not a prerequisite to proving the first patch.
3. **Query layer:** distinguish optimistic reachability from feasible prefixes, recovery, and surviving continuations. Keep the existing scalar/joint projections and shared successor implementation. Before promoting a candidate, identify which evidence establishes each claim; projected reachability alone cannot establish an executable prefix or successful continuation. If a concrete candidate needs a relationship the existing queries cannot preserve, add a focused coupled query over the existing semantics and return unresolved when it cannot establish the result. The SCC cache remains an execution optimization, not another model.
4. **Finding and synthesis layer:** keep `analysis.py` execution/role accounting, add stable mechanism identities and predicate/source provenance, and require a placement coverage result. An obligation may be ownership, a deposited-success flag, a guise state, or a disjunction; never force it through an item-only interface. `trigger` must return all unsafe-path interception sites or explain why placement is incomplete. `guards` verifies the actually placed transformations against the same action semantics, then compilation and runtime checks establish separate stages.

Exact reasoning about GK1's reviewed mechanisms does require **stateful relationships**: day with consumed latches, selected conversation with callback phase, scene with preparation, and entry with captured arguments. The later branch already preserves several of them. First complete the playable milestones with that machinery and identify any relationship it actually fails to carry through. Only then consider query-directed finite slices over the existing compiled machines or a stronger solver for a demonstrated bottleneck. Neither a whole-game symbolic solver nor a second permanent simulator follows from this review. If a query is incomplete, report unknown rather than silently cutting dependencies.

Keep the earlier games' frozen snapshots, patch sources/binaries, and established gameplay scenarios as integration constraints. If deeper migration becomes necessary, move one consumer at a time, with temporary differential scaffolding that has a deletion milestone. Do not preserve two semantic implementations indefinitely; remove each superseded reconstruction once the shared path owns its callers. A changed old-game result requires a source/game explanation, not an automatic golden update.

## Finite acceptance plan and stopping rules

**Milestone 1: ritual entry, end to end.** Derive the flag-216 obligation and both arming routes from source; generate a complete placement set; compile the changed pair; exercise a disposable original-version installation. Cover no mask, carried-but-unused mask, and successful mask use, including the independent walk-in route. Use ordinary inputs from reachable saves. Mark impossible combinations—such as selecting an absent inventory mask, or trying to walk after mask use has already started the cutscene—as unavailable, rather than forcing callbacks to fabricate a prefix. The patch must allow preparation, stop unsafe commitment before control is lost, permit retreat/retry without a repeated-dialogue hang, and allow prepared continuation. Record source site, exact predicate, emitted files, and runtime result under one finding identity. “Applied” or “report complete” is not completion.

**Milestone 2: confessional and Grace-room chain.** Reuse the later flag-351/scene evidence. Exercise neither deposit, either deposit, both deposits, and alternative signal devices; distinguish carried rod from deposited rod. Preserve return travel while preparation remains possible. Verify both guises at the actual scene closure, with Mosely's presence conditions respected. A correct preparation must never be rejected because the rod is no longer owned. This milestone tests setup consumed later and a boundary within one room.

**Milestone 3: one discovery result with a checked prefix.** Use the Cazaunoux/day chain as a negative control, not a promised softlock: callbacks must only follow their selected topic, and a day-4/flag-44-clear witness must either be demonstrated or refuted. Retain artist pickup and tile recovery controls as positive semantic boundaries. Remove any oracle shortcut that supplies the candidate's missing feasible prefix. Pin false-positive identities, not merely the names of two aggregate failing assertions.

For each milestone, require unchanged accepted behavior on LSL2, KQ4, KQ6, KQ5, and Dagger, using the relevant existing checks and gameplay boundaries. Run the full existing gate only at the integration boundary; do not launch hours of repeated whole-game analyses for every helper edit. No such experiment was needed to justify this review's diagnosis. The minimal next experiment is three ordinary ritual-entry controls—walk without the mask, walk carrying an unused mask, and use the mask successfully—on both original and patched builds, with retreat/retry checked after each refusal. No amount of extra projection testing can establish whether both input routes are intercepted safely.

Before evaluating performance changes, establish a same-input, same-hardware baseline with the source snapshot, build/cache state, and query workload recorded. Measure build/query time, peak memory, visited states, reused queries, and unresolved obligations against that baseline; attribute added cost to the specific semantic or validation work it buys. The historical timings above retain their experimental scope and are not prescribed ceilings for unlike inputs or machines. If resource limits interrupt a query, return unknown rather than removing a finding or validating a guard. If a playable milestone cannot preserve a needed relationship, identify the exact failed handoff before expanding the representation or query machinery. If a stronger query is then needed, measure its dependencies and cost before choosing another solver.

One-time SCI2 work includes resource layout/decompression, compiler selection and kernels, dialogue protocol/capture semantics, and generic scene/continuation handling. Recurring per-game work is identifying the resource version, confirming derived anchors and outcome meaning, resolving newly encountered source mechanisms, and validating actual failure/success controls. A catalog of manually prescribed item/day rules should not become the engine. A small evidence ledger is necessary validation, not a substitute for derivation.

The strongest objection is that the later branch may already contain enough semantic precision for every accepted GK1 case, making a larger action-contract migration slower than finishing synthesis. The source supports that objection: its scene and arrival obligations are far better than the old patch's inputs. Therefore the recommendation deliberately starts with a playable slice and allows existing machinery to prove itself. Successful end-to-end ritual and confessional patches, followed by source-checked day/callback queries without another reconstruction, would justify reducing the redesign to interface consolidation. Conversely, repeated incompatible prefix witnesses would justify a stronger coupled solver. What would **not** decide the issue is more green equivalence tests, more framework coverage, or another report-only finding count.
